## 2. Findings por severidade

### 🔴 ALTO (corrigir antes de prod)

#### F1. **Senha em texto plano no log de bootstrap**
**Arquivo:** `src/empresa/service.rs:177-181`
```rust
tracing::warn!(
    "🔐 BOOTSTRAP — Empresa {}: admin criado com senha ALEATÓRIA. \
     Guarde em local seguro (NÃO será exibida novamente):\n  \
     username: {}\n  \
     senha: {}\n  ...",  // <-- senha em texto plano no log
    empresa_id, username, senha
);
```
**Impacto:** Senha do admin vaza em logs (journald, syslog, arquivos de log). Logs são frequentemente compartilhados em resoluções de bug, podem vazar.
**Risco real:** ALTO em prod (log aggregation, screenshots, tail compartilhado).
**Sugestão:** Não logar a senha. Mostrar link/token de reset em vez disso. Ou truncar a senha (`senha: {}***`, `&senha[..2]`).

#### F2. **Query dinâmica com tabela de input externo (mesmo em teste)**
**Arquivo:** `src/empresa/repository.rs:298-303`
```rust
pub fn ping_count(pool: &mysql::Pool, tabela: &str, tenant_id: i32) -> Result<u32, ...> {
    let query = format!("SELECT COUNT(*) FROM {} WHERE tenant_id = ?", tabela);
    ...
}
```
**Status atual:** `tabela` vem de input externo mas função é `pub` e "usada em testes" (com `#[allow(dead_code)]`). Comentário do código diz: *"API intencionalmente exposta como `pub` para que os testes possam validar o defense in depth sem precisar importar o pool"*.
**Risco real:** BAIXO (uso restrito a testes internos), mas **se um dev futuro chamar com input externo, vira SQL injection**.
**Sugestão:** Hardcode as tabelas permitidas em `match` (whitelist):
```rust
match tabela {
    "usuarios" | "ordens_servico" | "clientes" => {},
    _ => return Err(ErroAplicacao::Validacao("tabela não permitida".into())),
}
```

### 🟡 MÉDIO (corrigir em sprint dedicada)

#### F3. **126 ocorrências de `.unwrap()` em código de produção**
**Distribuição por categoria:**
- `NaiveDate::from_ymd_opt(...).unwrap()` em `financial/service.rs` (3x) — risco BAIXO (input é year/month)
- Mutex lock `.unwrap()` (73x) — risco MÉDIO se a lock for poisoned
- Outros (50x) — varia; a maioria é parsing JSON ou conexão DB

**Sugestão:** Substituir `.unwrap()` por:
- `.unwrap_or(default)` quando há fallback razoável
- `?` com `From` para `ErroAplicacao` quando é erro real
- `.expect("mensagem útil")` quando é garantido pelo fluxo

**Não é blocker** (compilação é OK), mas se a GUI receber um panic, vai crashar.

#### F4. **Zero uso de `try_lock()` em 73 Mutex**
**Arquivo:** transversal
**Impacto:** Se um Mutex for poisoned (panicked durante hold), todos os outros clientes travam. Em prod, é uma faca de dois gumes: **fail-fast vs degradação graceful**.
**Sugestão:** Decidir conscientemente: `try_lock()` com fallback, OU `parking_lot::Mutex` (não poison).

#### F5. **`println!` em código de runtime (não tracing)**
**Arquivos:** `src/banco_de_dados/conexao.rs`, `src/banco_de_dados/init.rs`
**Status atual:** Logs de startup (não críticos)
**Risco:** BAIXO. Mas stdout não tem timestamps/levels como `tracing`.
**Sugestão:** Migrar pra `tracing::info!` / `tracing::error!`.
